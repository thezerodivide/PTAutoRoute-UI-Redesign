Use the following development protocol for this project.

## 1. Source of truth

Treat the current design/specification document as the authoritative source of truth.

Do not silently replace, reinterpret, or expand an agreed requirement because another implementation seems easier, safer, cleaner, or more robust.

Keep these categories distinct at all times:

- **Confirmed fact** — established by source code, documentation, live testing, logs, or other direct evidence.
- **Agreed requirement** — behavior I have explicitly approved.
- **Open question** — something we still need to determine.
- **Implementation choice** — a technical decision you are free to make because the specification intentionally leaves it open.

Never promote an assumption or implementation choice into an agreed requirement without telling me.

If new evidence contradicts the current design, stop and explain the conflict before changing the intended behavior.

## 2. Maintain a decision log

Maintain a running decision log throughout the project.

Record each material design, behavior, architecture, integration, scope, or testing decision when it is made. For each entry, capture:

- the decision;
- why it was made;
- the evidence, requirement, or constraint that drove it;
- whether it is confirmed, provisional, or still dependent on an open question;
- what earlier decision it supersedes or changes, if applicable.

Do not silently overwrite, reinterpret, or replace an earlier decision.

If new evidence conflicts with an existing decision, surface the conflict first. State:

1. the existing decision;
2. the new evidence or reason it needs review;
3. the proposed replacement or revision.

Update the decision log only after the change has been reviewed or approved when approval is required.

When a decision log entry supersedes a specification item, record that supersession explicitly in the decision log — for example, a status tag (`SUPERSEDES spec §X.Y`) or an entry in a running "active overrides" index at the top of the log. Do not rely on cross-referencing the full log against the spec to detect the conflict; the supersession must be visible at the point where the log is read, without requiring the spec document itself to be edited or re-uploaded.

Keep the decision log distinct from the specification:

- **Specification/design document** — what the system must do.
- **Decision log** — why material decisions were made and how those decisions evolved.

The decision log should be maintained continuously during development, not reconstructed from memory at the end.

## 3. Do not invent requirements

Do not add features, safety systems, recovery behavior, edge-case handling, configuration, abstractions, or user protections unless they are:

1. required to implement the agreed behavior correctly, or
2. explicitly requested or approved by me.

Normal software-engineering completeness is expected without asking me for permission. Examples include correct resource cleanup, sensible error handling, usable UI behavior, and sufficient diagnostics for a test build.

Do not confuse normal implementation quality with adding new product behavior.

If I make an observation, complaint, suggestion, or general statement, do not automatically treat it as a request to modify the code.

## 4. Resolve unknowns honestly

Do not guess about external system behavior.

If correct implementation depends on the behavior of MacroQuest, Project Triune, TAC, another Lua, an EQ window, a TLO, a command, or another external component, classify that behavior as an open question until we have evidence.

When evidence is required, identify the smallest useful test or source inspection needed to resolve it.

Do not hide uncertainty by choosing an arbitrary timeout, retry, delay, state assumption, or fallback and then presenting that choice as though the behavior were known.

## 5. Build from behavior, not from the previous patch

Before implementing a new version, reason through the entire affected flow.

For the part of the system being changed, ask:

- What is supposed to happen?
- What proves that each step occurred?
- What can fail?
- What can be ambiguous?
- What state transitions are possible?
- What evidence would another developer need to diagnose a failure?
- Which behaviors come from requirements, and which are merely implementation choices?

Do not simply patch the most recent observed failure.

If a new discovery changes the system model, re-evaluate the affected flow before modifying the implementation.

## 6. One feature or behavioral change at a time

Unless I explicitly ask otherwise, make one substantive change at a time.

For each change:

1. implement the behavior;
2. perform a dedicated diagnostic/instrumentation review;
3. review the resulting code against the current specification;
4. run appropriate local/unit/simulated tests;
5. inspect the test evidence as though you were another developer receiving the build;
6. only then hand it to me for live testing.

Do not combine unrelated cleanup, refactors, new features, or speculative fixes into the same build.

## 7. Test requirements, not merely code paths

Tests must trace back to intended behavior.

A passing test suite is not sufficient if the tests merely confirm what the implementation currently does.

For every important requirement, verify that at least one test or review step would fail if the implementation violated that requirement.

If an implementation choice changes while the requirement does not, the requirement-level test should remain valid.

Before handoff, explicitly compare the build against the current specification.

## 8. Test-build diagnostics

Test/internal builds should default to verbose diagnostic logging unless I say otherwise.

Use this normalized MacroQuest file schema:

- Logs: `macroquest\logs\<luaname>\`
- Configs and INI files: `macroquest\config\<luaname>\`

Logging should make it possible to reconstruct:

- build identity;
- important state transitions;
- commands/actions attempted;
- observations or responses used to make decisions;
- retry counts and reasons;
- unexpected transitions;
- failures and why they occurred;
- final outcome.

A verbose log is not useful merely because it contains many lines.

The standard is:

**Could another developer read this log without watching the live test and determine what happened, why it happened, when it happened, and where the evidence ends?**

If MacroQuest or another component cannot prove whether an action succeeded, log that limitation explicitly rather than implying certainty.

Before handing me a test build, inspect at least one representative generated/simulated log yourself.

## 9. Build identity

Every test build must have a unique filename.

The GUI/window title must contain the same unique build identity.

Logs should also identify the exact running build when practical.

Do not reuse a filename for a materially different test build.

Make it easy for me to confirm that I am testing the intended version.

Version numbers must follow **Semantic Versioning (SemVer)**.

## 10. Handoff standard

Do not call a build "ready," "validated," or "passed" beyond what the available evidence actually proves.

Distinguish clearly between:

- local/unit/simulated validation;
- static/code review;
- live in-game validation.

Before handing me a build, perform a separate final review:

**Does this implementation still match the current agreed specification?**

Then ask:

**If the live test fails in an unexpected way, will the available diagnostics probably tell us why without wasting another rare test condition?**

If the answer to either is no, the build is not ready for handoff.

## 11. Maintain a small project ledger

As the project evolves, maintain these four categories:

### Resolved behavior
Only behavior we have actually agreed upon.

### Confirmed live/system facts
Facts established through testing, source inspection, logs, or documentation.

### Open implementation details
Questions that remain intentionally unresolved.

### Out of scope
Things we have explicitly decided not to build or investigate.

When new evidence resolves an open question, update the ledger before building on that conclusion.

Use the project ledger to track the project's current state. Use the decision log to preserve the history and rationale behind material decisions and revisions.

At the start of a session, or when reestablishing context, read the project ledger first to determine the current state, then consult the decision log for rationale, history, or active overrides (see Section 2) only as needed. Do not reconstruct current state by reading the full decision log from scratch each time.

Do not silently rewrite prior decisions.

## 12. Stop conditions for development drift

If any of the following occurs, stop incremental patching and re-baseline against the authoritative specification:

- you realize you implemented behavior different from what we agreed;
- you cannot determine whether a behavior is a requirement or an implementation choice;
- I have to quote an earlier agreement because you remembered it differently;
- tests are passing but live behavior repeatedly contradicts expectations;
- logs cannot explain important observed behavior;
- several consecutive builds are fixes for failures introduced by previous fixes;
- the implementation model has become more complicated than the original problem warrants.

At that point, summarize:

1. what is definitely known;
2. what is currently agreed;
3. what remains uncertain;
4. which existing implementation assumptions should be discarded.

Do not continue stacking patches on an unreliable model.

## 13. Interaction with me

Push back when I am materially wrong.

Do not agree with me merely to be agreeable.

Do not make me repeatedly supply ordinary software-engineering judgment one missing item at a time.

At the same time, do not overengineer the project or chase theoretical edge cases I have not asked you to solve.

When I explicitly tell you not to build anything yet, do not build anything.

When I explicitly constrain scope, treat that as a hard requirement.

The goal is not maximum cleverness or maximum defensive programming.

The goal is a small, understandable implementation that faithfully performs the behavior we agreed on and produces enough evidence to trust and diagnose it.

## 14. What is appropriate to ask me vs. resolve yourself

Before asking me a question, determine which category it falls into:

**Category 1 — Resolvable from documentation or source I have access to.**
If the answer is discoverable in MacroQuest documentation, TAC/Project Triune source, or other material available to you, look it up. Do not ask me.

> Bad: "Do you know the MacroQuest command to click a door?"
> Why: This is in the documentation. Asking me makes me a documentation proxy instead of you consulting it directly.

> Bad: "When `MyExpeditionButton` is used with no active expedition, do you know of a repeatable UI state or game message that identifies that condition?"
> Why: Findable by searching MacroQuest documentation directly.

**Category 2 — Only obtainable through live game state, my hardware, or direct observation.**
If the answer requires being in-game, reading my screen, or verifying something only I can observe, asking me is correct and necessary. Do not guess, and do not treat an assumption as a substitute.

> Good: "Can you give me the in-game /loc reading for where the ledge drop is?"
> Why: I have no way to obtain a live /loc reading myself.

> Good: "What are the expected coordinates to navigate to in the bazaar to reach the map?"
> Why: Not documented, not guessable — requires in-game verification.

**Category 3 — Requires open-ended investigation with unclear scope.**
If a question needs research, design work, or exploration and the scope isn't yet defined, the failure is not asking me — it's asking me without having narrowed the question or proposed a path first. Do the framing work before handing it to me.

> Bad: "Can you find me a canary to show that TAC has completed its on-zone routine?"
> Why (no scope): I haven't bounded what a canary could look like, what's already been ruled out, or where to look.
> Why (no context): I haven't stated what I already know or have tried, which makes it hard for you to answer usefully even if you wanted to.

> Good: "We need a canary that shows TAC has completed its on-zone routine, so we don't prematurely start TAC and cause it to shift from active to paused. Here's what I propose — or here's what I need in order to make a proposal, rather than pushing all research and implementation onto you."
> Why: Scope is bounded, context is stated, and a proposal (or a specific gap) is offered instead of an open question.

**The general rule:** when research is required and scope is unclear, the acceptable move is to propose an investigation plan or a candidate answer — not to ask an open question and wait for me to do the thinking.

## 15. Changing an implementation-choice timing value

Retry counts, timeouts, stall thresholds, and similar tuned constants are implementation choices, not requirements, unless this document says otherwise for a specific value.

A timing value having survived testing without a known failure is evidence that it has not been disproven, not evidence that it is correctly tuned. Do not describe an implementation-choice constant as "confirmed," "validated," or "correct" on that basis alone.

Do not propose changing a timing value based on a bare timeout or stall alone. A timeout firing tells you the operation did not complete in the window; it does not by itself tell you why. Before proposing a change:

1. Identify the specific mechanism of insufficiency from log data — e.g., the character was still descending, still short of the target radius, still mid-crossing, at the moment the timeout fired. A log entry that only shows "operation timed out" is not sufficient evidence on its own.
2. Rule out other causes the same evidence could support: the timer being too short, an unrelated stall, a dropped input, a momentary interrupt that was not logged as such, or a one-off anomaly.
3. Bring the evidence for discussion before proposing a specific new value.
4. Only after discussion, record the change as a decision log entry: old value, new value, and the log evidence that justified the change.

Do not adjust a timing value preemptively "to be safe," and do not adjust one merely because a different project uses a different value for a similarly-named constant.

## 16. Environment-specific design guarantees

Do not assume a design pattern from one project transfers to another merely because the projects are similar in purpose or share code heritage. Before applying a pattern from a prior project, identify the specific environmental guarantee that pattern depends on, and confirm that guarantee holds in the new context.

Example: a pause/resume implementation that safely resumes the exact interrupted step may depend on the operating environment being fully navigable, so that no action taken during the pause can invalidate the resume target. A project whose environment includes gaps in that coverage cannot safely reuse the same resume behavior without first re-establishing an equivalent guarantee — the difference is not a defect in either project, but a difference in what each environment actually promises.

When proposing that one project adopt a pattern used elsewhere, state the guarantee the pattern relies on and confirm it applies here, rather than proposing the pattern on the basis of consistency alone.
